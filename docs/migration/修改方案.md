### 0.1 WHO TRIGGERS PAYS（冻结契约）

1. 经过可信认证的 initiator/triggerer 是该 logical operation 的 payer；所有实际 billable child work 都继承该 payer。
2. resource/access owner 只表示访问、存储或资源归属；平台 owner 0 可以存在，但永远不能成为 payer fallback。
3. 同一 operation 的 retry/recovery/requeue/lease reclaim 必须恢复原 triggerer、run、execution provenance；只有明确创建真实新 operation，才允许新的 authenticated actor。
4. 浏览器 UID、owner、current worker、sponsor/shared key、route、provider default 或 tool _meta 不得决定 payer。缺 actor 的 paid work 必须 fail closed/quarantine，不能自动“找一个”付款人。
5. 本地确定性 CPU/DB/Tika/BM25/cleanup 工作不凭空收费；model-side inline tools 与模型调用按已确认折扣契约处理，独立 MCP service fee 仍独立但使用同一可信 triggerer。

## 2. 推荐架构

采用“保留 Chat 完整后端 + Sub2 身份与钱包适配层”。两个应用各自保留应用数据，但身份与资金只保留一个权威来源。

```text
浏览器 -- chat 独立域名 --> Chat 前端 / 后端
                              |-- Chat 会话、消息、文件、知识库、工具配置、偏好
                              |-- 外部身份适配 --> Sub2 统一登录
                              |-- 模型与权限适配 --> Sub2 目录 / 请求准入
                              |-- Chat 价格策略发布 --> Sub2 确认版本 / 按策略结算
                              |-- 用户级调用适配 --> Sub2 Gateway --> 上游模型
                              |-- 财务操作适配 --> Sub2 钱包 / 账务 / 支付服务

Sub2 页面 --------------------> 同一套 Sub2 账号、钱包、账务与权限服务
```

图中的适配层及缺失契约属于拟新增能力。Chat 只连接 Sub2；实际账号、供应商 Base URL、API Key/OAuth Token 留在 Sub2，由其按获准分组调度，不逐个复制到 Chat。

## 4. 统一登录与身份绑定设计

- 先核对通用 `UserIdentity`、`AuthRepository` 与现有 Sub2 专用绑定/登录接点（C02—C04、P35-08/P35-09）；确定一致的稳定主体关联并复用现有能力，不无依据新增重复映射表。通用身份表存在不表示专用绑定已被所有安全检查识别。
- 推荐 Sub2 作为统一身份提供方，通过授权码流程让用户在 Sub2 完成密码、验证码和二次验证；已经登录 Sub2 的用户可复用其有效登录态。
- Sub2 是否已有身份提供方端点必须区分于“Sub2 支持使用第三方 OIDC 登录”。消费身份不等于提供身份。
- 若当前 Sub2 缺少授权端点，列为 Sub2 侧前置改造，不能承诺仅修改 Chat 即实现完整 SSO。
- 使用稳定的 `(issuer, subject)` 关联 Chat 本地用户。首次可信登录创建无本地密码的用户，先按 R11 映射角色再签发会话；普通外部用户仍为普通角色。邮箱仅为可变资料，不作为静默合并依据。
- Chat 会话与 Sub2 会话分属各自应用。设计精确 redirect allowlist、一次性短时授权码、state、PKCE，以及所选协议要求的 issuer/audience/nonce/签名校验；不在 URL 中携带 access/refresh token。
- 禁用、改密、退出全部会话、解除绑定后的访问撤销必须覆盖新登录、refresh、既有会话和后台任务；确定撤销时效并测试失效窗口。
- 用户和资金权限不能由浏览器传入的 user_id、group_id、价格、倍率或余额决定。

## 5. 单一钱包与防双重扣费设计

### 5.1 唯一资金写入方

集成模式下，所有实际资金变化只能由 Sub2 的既有业务服务执行。Chat 本地余额、预留、结算、支付回调或管理接口不得再产生独立货币变动。可以保留请求状态与账务引用，但不能把引用记录当作第二本资金账。

### 5.2 请求与计费归因

每次模型执行必须使用服务器端绑定到真实 Sub2 用户及合法授权范围的调用身份进入 Sub2 Gateway。具体凭证方案须核验现有 API Key 服务后确定。禁止全用户共用单个扣费 Key，禁止把服务或上游 Key 发给浏览器。

将“用户的一次操作”“Chat run”“实际上游执行”“Sub2 usage/账务记录”分别标识并关联。一条用户消息可能触发主回答、工具回合、摘要、embedding 等多次真实执行；应分别核算真实费用，不能把“用户点击一次”误判为只能有一条合法 usage。

### 5.3 幂等、取消与失败

- 为受控财务命令设置稳定幂等键，绑定用户、操作类型、原始业务标识及请求摘要；同键不同参数必须拒绝。
- 不假定现有 Gateway 支持任意 `Idempotency-Key` 或仅靠客户端传 UUID 即有去重保证。
- 传输断开但执行结果未知时，进入待核对状态，先查询已有执行/账务结果，不盲目重发可能已计费请求。
- 浏览器断线恢复仅重放既有流事件，不重跑上游；用户明确重新生成是新的执行，使用新标识并按真实用量计费。
- 取消、部分输出、上游失败、支付回调重试等按 Sub2 最终账务规则处理；取消不等于必然免费或自动全额退款。
- Sub2 或必要校验不可用时 fail closed，不降级到 Chat 本地钱包、公共服务 Key 或绕过鉴权的直接 provider 请求。

### 5.4 完整功能覆盖

普通聊天、临时聊天、重生成、工具循环、图片/视频、embedding/RAG、文件处理中的模型调用、记忆与摘要等，都必须逐项列出实际执行与收费路径。Sub2 暂不支持的协议或费用类型是实施缺口，不通过隐藏功能或不计费绕过。

## 6. 管理后台保留原则

账号、余额调整、赠送、充值、兑换、退款及套餐等重叠界面可以保留，实际身份/资金操作仍落到 Sub2。Chat 模型零售价与玩家优惠保留在 Chat 管理，经 Sub2 确认的应用价格策略版本才可用于结算；这不是维护全站 Sub2 原价格配置的越权通道。各操作保留操作者、目标用户、来源应用和幂等关联；金额单位、精度、舍入、临时余额有效期及套餐关系须明确映射。

不能假定两套系统现有的套餐、折扣、兑换码或支付渠道语义等价。逐模块核验后建立映射矩阵；缺少 Sub2 对应能力的操作进入前置依赖清单。

## 7. 存储、部署与回滚原则

- 可复用同一 PostgreSQL 实例，但建议独立数据库/业务表与账号；不让 Chat 的自动迁移器接管 Sub2 表。
- Sub2 账号、余额及历史迁移不因本次集成重建、重编号或改写。
- 两个域名独立 HTTPS 与会话边界；服务间地址使用受控内网/回环地址和独立凭证，并限制外部可达性。
- 反向代理须覆盖原流式协议、上传限制、取消、断线恢复、超时和可信代理规则；同机部署不等于天然可信。
- 灰度与回滚期间，已经接入 Sub2 钱包的用户不得自动回退到旧 Chat 本地资金模式。资金权威切换只能在停止新请求并核对在途执行后进行。
- 本轮不实施部署、建表或测试数据删除。
## 8. 可行性结论、方案取舍与边界

### 8.1 可以支持的结论

**有条件可行，推荐进入契约设计和受控开发，而不是直接改数据库上线。**

1. Chat 已有完整应用后端和本地用户/会话、外部身份绑定、聊天流及账务相关接点，具备保留后端并增加适配层的基础（C01—C12）。
2. 历史身份专项在 B01 快照观察到 Sub2 内部身份关联及会话版本/状态检查（S01—S03）。本次 P3.5 为不同 HEAD，新增证据只覆盖 B05 与 P35-01—P35-13；不把旧身份专项自动升级为当前完整审查。
3. 当前证据**没有证明** Sub2 已提供完整 OIDC Provider，也没有证明当前 `main` 已提供符合本方案的用户级服务凭证、钱包命令幂等或执行状态查询契约。它们是前置工作，不是可直接调用的现成功能（GAP01—GAP06）。
4. Chat 的本地资金写入覆盖、全功能调用计费和两边套餐/支付语义对齐，决定改造规模。不能把本任务估成改一个数据库连接串或一个 API 地址。

### 9.2 推荐主流程

1. Chat 服务端发起登录事务，生成并绑定 state、PKCE challenge，以及所选 OIDC 流程要求的 nonce。
2. 浏览器跳转到 Sub2 的**拟新增/待确认**授权入口；密码、验证码、2FA 在 Sub2 原认证链完成。授权页不得依靠 URL 中的用户 ID 建立身份。
3. Sub2 对精确白名单 callback 返回短时、单次 authorization code。浏览器 URL 不承载 access token、refresh token、服务密钥或余额。
4. Chat 服务端完成 code exchange，验证响应来源、issuer、audience、subject、时间、签名和 nonce 等约束；禁止算法降级和未受信 JWKS 来源。
5. 按可信 issuer/subject 查找现有绑定；取得同一主体的权威角色/状态后，事务性创建或同步本地用户、映射角色与绑定。管理员首登和已有错误普通角色均按 R11 处理。
6. 核验并保证绑定唯一性、并发创建幂等、跨 issuer/环境隔离。已有同邮箱用户触发显式冲突流程，不静默关联。
7. 绑定与角色写入成功后，Chat 才签发含正确角色的应用会话。访问会话/文件仍用本地 ID；访问 Sub2 使用可信绑定及受控凭证。角色缺失、未知或来源不可信时返回明确认证错误，不静默降为 user 或保留旧高权。

**建议协议而非已存在端点：**如果采用 OIDC，discovery、authorization、token、JWKS，以及需要时的 userinfo/logout/revocation/introspection 能力必须形成明确契约；不能仅新增一个“返回用户 ID”的 callback 就称为完整 SSO。端点实际路径在 W01 锁定，本文不虚构现有 URL。

### 9.3 可信角色映射与生命周期

本轮用户明确批准下表，替代旧方案“新影子用户固定普通角色”“Sub2 管理员还须由另一名 Chat 管理员手工授予后台角色”的规定。两边超级管理员字符串不同，必须显式映射。

| Sub2 经验证的角色 | Chat 角色 | 必须具备的首登结果 |
|---|---|---|
| `user` | `user` | 普通用户，不获得管理后台权限 |
| `admin` | `admin` | 首次成功登录即可进入管理员后台、调用其角色允许的管理接口 |
| `super_admin` | `superadmin` | 首次成功登录保留超级管理员能力，不降为普通管理员 |

- 角色来自受信 Sub2 服务端，绑定 issuer、audience、稳定 subject、账号状态和权限新鲜度；角色/权限版本的实际字段由 W01 锁定，不能假定现有 identity epoch 必然随角色变化。不得信浏览器参数、邮箱、余额、premium/玩家等级、服务 Key 身份、provider 全局默认角色或“第一个登录者”。
- 先验证身份及角色，再事务性创建/同步本地用户和绑定，最后签发会话；并发、回调重放或写入失败不能留下错误普通角色、重复用户或错误管理员会话。
- 已绑定账号在每次登录/refresh 时重新同步；以前被误建为 user 的真实管理员要纠正，Sub2 升降级也要同步。本地直接改角色不能覆盖已映射的权威角色；保留 Chat 自身功能权限实现，但不得再设手工授权门槛阻断已映射管理员进入其后台。
- 禁用、降权、解绑、全局退出要覆盖既有会话、管理 API、后台任务和在途执行策略；在 W01 约定的 `T_revoke` 内撤销旧高权。敏感操作须使用有效权限版本/必要的权威复核，不能只读旧 JWT 中的角色。
- Chat 管理员身份不额外授予 Sub2 调账、组授权、用户管理或全站价格维护权限；相关跨系统操作仍校验 Sub2 对原操作者的授权。API Key 服务身份不继承人的超级管理员权限。
- 注册、改密、找回密码、2FA 和账号状态实际由 Sub2 负责；头像、偏好等本地资料分清权威字段，不按邮箱静默合并测试账号。

### 9.4 首次管理员可达性与 SSO-only 切换

- SSO 信任配置及角色映射须能通过已授权的部署初始化，不得要求“先有一名 Chat 管理员进入后台，才能启用首个管理员的映射”；普通本地注册开关不能阻断可信 Sub2 管理员首登。
- 登录和按角色进入管理后台不依赖钱包余额、已配置上游、已上架模型或付费执行契约。资金/模型契约缺失只能关闭对应付费能力，不能阻断管理员修复配置的入口。
- 启用 SSO-only 前，用真实受控的 Sub2 `super_admin` 完成登录、后台进入及必要超级管理员接口验收；同时验收 `admin` 的后台入口。仅查数据库存在管理员行不算可达性通过。
- 将 Sub2 专用绑定、可信角色和有效认证路径纳入“至少一个活跃、可登录超级管理员”的检查。当前 `HasActiveSuperAdminIdentity` 只查通用身份关系（P35-09）；不能仅改 JIT 角色后就假定守卫已满足，也不能删除守卫绕过验证。
- 主动解绑、修改登录方式或本地降权不得移除最后一条有效超级管理员登录路径；但 Sub2 已确定的禁用/撤权必须生效，不能为避免锁出而保留失效高权。此时明确报警并通过 Sub2 权威恢复，不自动启用普通本地密码后门。
- 不擅自保留或新增 break-glass 账号；如运维确有需要，须单独批准、隔离入口、最小权限并审计。SSO 服务故障不承诺无条件继续高权访问。

### 10.1 凭证方案的前置核验

优先评估 Sub2 现有用户级 API Key 管理是否满足用户归因、目标组选择、模型范围、额度、有效期、轮转和撤销；不能从“Gateway 支持 API Key”推导出“已经满足 Chat 托管凭证”。

- 若复用托管 Key：Sub2 负责合法发放和约束，Chat 仅服务端加密保存必要引用/凭证，不改变用户正常 Key 的管理含义，不默默创建无限权限 Key。
- 若采用新增 subject exchange：只接受可验证且限定 audience 的服务请求和用户授权上下文。禁止服务凭证配任意 `X-User-ID` 就代替全体用户。
- 不把 Sub2 Key 配为 Chat 全站共用 upstream Key。必须在实际执行时从可信用户上下文选取凭证；否则请求可能全部记到一个账号。
- 异步任务持久化不可变的身份/用途关联与凭证引用，不持久化明文密码或浏览器 token；执行时重新检查账号、凭证及模型权限。

### 10.2 Chat 零售定价与 Sub2 结算

**2026-09-14 用户批准：Chat 管理价格规则，Sub2 按规则结算。**此决定替代原方案“所有模型价格均由 Sub2 制定”的约束，不改变身份、模型准入和资金账本的权威归属。

- Chat 管理本应用的模型零售价、玩家分组及优惠。玩家组与 Sub2 路由/权限组不是同一概念，也不要求一一对应；Chat 玩家身份不能扩大 Sub2 模型或组授权。
- 经受控服务发布完整、不可变的价格策略版本，由 Sub2 确认应用、生效范围、金额单位和支持的计费类型。尚未确认的版本不得用于新付费执行；接口、字段及发布机制均为拟新增契约，不是 P3.5 已具备的端点。
- 每次实际执行绑定可信用户、来源应用、模型/协议、价格版本、玩家优惠版本、请求摘要和执行标识。单价与倍率不能在结算时无声明地重新读取最新值；历史账单及退款关联原版本。
- Chat 来源只选择一条 Chat 零售策略，不再额外叠加原 Sub2 分组、个人、高峰或动态零售倍率；若产品确需某项因素，应显式写入 Chat 策略而非隐式继承。普通 Sub2 API 调用保持原定价，不能通过伪造应用标记切换策略。
- Sub2 从可信执行链取得实际用量，按已确认策略计算并执行唯一结算。禁止浏览器提交任意价格/金额，禁止普通 Gateway 先扣旧价后再补扣/退差价，禁止用管理员增减余额接口模拟消费结算。
- 区分上游真实采购成本、原倍率前计费额、Chat 零售价与最终实扣；P3.5 的 TotalCost 不自动等于真实采购成本。账号成本统计、Key 配额和订阅额度的口径须在 W02 明确，不因零售价迁移而漏计或重复累计。
- 目录展示不等于授权。最终可执行范围仍为 Sub2 用户、组/Key 限制与 Chat 限制的交集；不把展示配置擅自转换成请求拒绝规则，也不以展示可见扩大权限。
- Chat 保留模型选择、参数和价格管理能力，但不保留独立货币扣减。维护非 Chat 的 Sub2 原价格配置仍需要 Sub2 的独立管理授权。

### 10.3 临时余额与现有资金语义

本方案沿用 Sub2 永久/临时余额机制。本次 P35-03/P35-04 补充了费用入账口径与事务组织的静态证据，但没有完成过期、冻结/预留、退款恢复、套餐并存及缓存/并发的完整核验；不能将价格策略改造当作重写这些资金语义的授权。历史目录线索不能补足当前运行证据。

W02 必须形成“现有规则快照 + 对应测试预期”，并由适配器复用，不在 Chat 重写一份金额算法。不假定临时额度可随意转永久余额，也不假定退款一定返还到当前可用余额。

### 10.4 “上游”中的 Sub2 分组与模型选择

**本轮批准的是新增接入能力，不是当前已经可用的多选控件或接口。**现有端口和回退/调度缺口见 P35-11—P35-13、GAP09。

#### 10.4.1 管理界面与职责

| 项目 | 设计要求 |
|---|---|
| 接入类型 | 在原“上游”中新增“Sub2 账号池”，复用服务地址与应用信任配置，不逐个导入池中账号 |
| 允许分组 | 管理员多选稳定 `group_id`；显示名称、平台、公有/专属、启停状态、可用账号数及数据新鲜度；同名或改名不改变身份 |
| 模型同步与上架 | 按所选组同步模型/协议能力，去重时保留来源和明确模型映射；管理员再选择上架范围。目录展示不等于调用授权，也不把 Sub2 展示配置当完整能力证明 |
| 路由优先级 | 同模型有多个获准组时可设置优先级；组内账号选择、实际供应商 URL 和凭证仍由 Sub2 负责 |
| 生效规则 | 保存/发布经服务端确认的白名单和配置版本；新增分组不自动加入，空选择/配置缺失不表示全量开放。新模型先确认能力及已发布价格策略再开放付费 |

分组列表读取不等于拥有池调用权；管理操作校验 Chat 功能权限及 Sub2 授予该应用/操作者的配置权限，不把全权限管理 Key 发给浏览器。停用组可显示原因，但不能通过勾选绕过状态；可用账号为零时不得自动借用未选择组。

#### 10.4.2 实际执行边界

每次执行必须同时满足：**应用已确认允许组 ∩ Sub2 当前用户有效组权限**，以及组状态、订阅/Key 约束、真实模型能力和 Chat 模型上架/功能限制。分组 ID 和应用来源不由浏览器自行指定后直接信任。

- 管理员勾选专属分组不会自动授予未授权玩家访问权；公有组仍受 Sub2 的受限用户规则，订阅组仍须有效订阅等原有检查。本次未单独批准“Chat 应用代所有玩家访问专属池”；若未来需要，须明确批准并在 Sub2 建立独立受控契约，不改变本次交集默认。
- Sub2 对初始调度、所有安全可重试的 fallback、Composite 后续路径、HTTP/WebSocket 和异步任务均校验最终组及账号归属；切换只能发生在允许集合内。Simple 模式若不能保持该边界，应拒绝 Chat 付费执行，不回退到按平台全池查询。
- 仅在确认可以安全重试时按优先级切组；已派发而结果未知仍按 UNKNOWN 查询/核对，不因换组而重跑可能已收费的执行。
- 分组停用/删除、用户权限撤销、白名单移除或模型下架后，新派发/下一次重试和后台执行重新验证。配置版本用于追溯，不允许旧快照使已撤销权限继续有效；在途处理规则由 W02 明确。
- 执行记录关联应用、用户、白名单版本、请求模型、候选/最终组、实际账号引用及价格策略版本；审计端可追溯但不向普通用户泄露池配置或密钥。
- Chat 来源继续按 R05 的已确认零售策略结算，不因组选取或回退再叠加原 Sub2 零售倍率；普通 Sub2 API 保持原规则。

## 11. 防双重扣费的工程闭环

### 11.1 两类不同的重复问题

1. **双系统重复扣费**：一次上游执行经 Sub2 扣费后，Chat 自己的预扣/结算又减少本地资金。解决方法是单一资金权威与所有本地资金写入路径的控制。
2. **同系统重复资金操作**：网络重试、重复回调或故障恢复使 Sub2 对同一业务操作重复生效。解决方法是权威端幂等、执行查询、状态机与核对，而不是只在 Chat 前端禁用按钮。

二者都必须通过 G-NO-DOUBLE-DEBIT。

### 11.2 集成模式的强约束

建议新增一个明确、可审计且不能按单次请求任意切换的“Sub2 资金权威模式”。配置名字由实施确定，不将本方案中的概念名当现有配置项。

- 启动时核验身份/资金契约及配置，发现不兼容就阻止进入付费服务状态。
- Chat 本地预留、余额扣减、赠送、退款、套餐抵扣、支付入账和管理员调账统一经过权威适配边界。
- 允许保存 Chat 价格规则、玩家优惠、发布版本、使用统计、运行状态与权威账务引用；禁止本地资金写入不等于禁止价格管理，但这些记录不能驱动第二次货币结算。
- 不通过全局关闭某个现有 billing 开关就假定所有资金路径已被覆盖；要审查路由、服务、repository、job、callback 和启动种子。
- 尽可能通过数据库角色/接口权限强化边界；Chat 不持有 Sub2 业务表的直接写权限。
- 回滚、配置丢失、Sub2 故障均不得自动恢复本地货币扣费。

### 11.3 建议的执行状态机

```text
CREATED -> AUTHORIZED -> DISPATCHED -> SETTLED / FAILED
                              \----> UNKNOWN -> RECONCILED
```

这些是设计状态，不是声称当前数据库已有相同枚举。

- 一个实际执行使用稳定执行标识；相同执行重试/查询沿用该标识，新生成或新工具回合使用新的执行标识。
- 在发送前持久化必要的执行归因，保存上游/网关响应关联。崩溃恢复不得丢失“可能已经执行”的事实。
- `UNKNOWN` 不等于失败、未扣费或可以重发。先查权威结果；没有查询能力时隔离并人工核对，作为发布前缺口处理。
- 不宣称网络和 provider 全链路具备 exactly-once。需要证明的是：受控资金操作不会重复生效，未知执行不被盲目重放，真实用量可对账。
- 若当前 Sub2 对所需操作没有权威去重/查询能力，仅改 Chat 不能给出足够保证；该能力必须在 Sub2 前置范围中补齐或制定经批准的严格不重试与核对策略。

### 11.4 对账要看什么

对每个测试用例，记录 `application + Sub2 user + Chat run + execution + group policy revision + final group + account reference + pricing revision + player policy revision + usage + transaction` 的可追溯关系；这些标识的实际字段在 W02 锁定。

- 校验资金账务的实际变化，不只看 UI 余额、HTTP 成功或日志条数。
- 分别证明 Chat 不产生第二次货币变动、Sub2 同一业务操作不重复生效。
- 对永久/临时余额、赠送、退款和过期事件分别核对，不用总余额的偶然相等掩盖重复扣费后又重复退款。
- 并发测试区分合法的多个真实执行，不把多条真实计费误报为重复。一次逻辑结算可合法形成多条临时额度消耗或资金分录，不能以数据库行数必须为一来定义防重复。

“保留”是目标；源码入口存在不是完成验收。以下矩阵同时作为 W06—W08 的覆盖范围，实施时按当前代码继续补齐，不以列表未写到为由删除功能。

## 14. 数据、上线与回滚细化

### 14.1 无正式迁移不等于可以清库

- 无需合并真实 Chat 用户、余额或历史资金；不设计把 Chat 测试余额导入 Sub2 的迁移。
- 开发测试可使用显式测试账号和隔离测试库。现有本地数据保留，清理需要另行授权。
- 生产采用可信首次登录建用户或显式管理员绑定。影子用户不能因测试邮箱碰撞绑定到真实 Sub2 用户。

### 14.2 数据库和迁移

同一 PostgreSQL 实例可降低运维成本，但不是共享资金的必要条件。推荐 Chat 与 Sub2 分离数据库/账号；若选择同库不同 schema，必须明确连接的 search_path、表名映射、迁移权限和备份恢复边界。

Chat 的 GORM 自动迁移路径已有静态线索（C08），不能让它指向 Sub2 业务 schema。新增绑定/执行关联所需字段优先复用现有实体，补充约束要使用各项目正式迁移机制；Sub2 历史迁移保护在当前 `main` 重新核验后执行，禁止修改已应用历史 SQL。

### 14.3 发布顺序

1. 独立环境完成契约、单元、数据库及双应用集成测试。
2. 部署 Sub2 必要的向后兼容能力，先不向普通用户开放 Chat。
3. 初始化 SSO 信任及映射，先验收 Sub2 管理员/超级管理员的首次后台可达与最后有效登录路径，再切换 SSO-only；资金/模型未就绪时仅关闭付费能力，不阻断管理入口。
4. 配置 Sub2 账号池允许组、模型上架和 Chat 价格版本；用受控用户完成全功能、最终组及回退边界、无本地资金/provider 旁路与权威账务核对。
5. 小范围灰度，持续观察重复操作、UNKNOWN 执行、余额差异、撤销延迟及失败关闭。
6. 所有阻断门禁通过、未解决财务差异为零后，才允许正式开放。

### 14.4 回滚规则

发现重复扣费、跨用户归因或权限绕过时，首先停止新的付费执行；保留在途状态和证据，按权威记录核对。

- 可以关闭 Chat 入口或回滚其展示/非资金功能。
- 不允许把集成用户自动切回 Chat 原本地钱包；不允许为回滚重新放开旧的直接 provider 调用。
- 恢复前核对所有 UNKNOWN 与在途执行；退款等修复操作必须由 Sub2 授权、幂等、留痕地执行。
- 新增数据库变更应以兼容、可前向修复为优先，不假定删除列、回退历史迁移或还原整个共享实例是安全回滚。
