- [ ] 不按邮箱静默合并，不通过浏览器传入 user_id/role 建立绑定。
- [ ] 普通注册、改密、找回和 2FA 入口接入 Sub2 权威；不留下独立认证旁路。

## 5. 验收环境、数据与参数

### 5.1 测试环境要求

- 使用隔离数据库、独立测试用户、明确区分的测试 issuer/client 与受控凭证；不要使用正式用户金额做故障注入。
- 保存测试前后权威资金明细与 Chat 资金写入观察，不保存密码、token、Key 或真实聊天正文。
- 所有临时余额测试使用可控时钟或明确时间窗口，避免把自然过期误判为扣款。
- 并发用例区分合法的多次执行与同一逻辑操作重放；凭证、操作 ID、用户、模型、价格条件可追溯。
- 在 W01/W02 固定 `T_revoke`、幂等记录保留窗口、状态查询超时、金额精度与价格版本策略；任何未定参数都不能凭肉眼认定通过。

### 5.2 统一证据模板

每条验收记录至少包含：

`用例ID / 时间 / 源码快照 / 环境 / 前置数据 / 注入点 / 输入 / 预期 / 实际 / 通过或失败 / 审核人 / 证据路径`

对付费操作追加：

`来源应用 / Sub2用户 / Chat用户 / run / 实际执行 / 组配置版本 / 最终组与账号引用 / 价格及玩家优惠版本 / 逻辑结算 / usage / 资金分录或事务引用 / 幂等键 / 请求摘要`

对身份/后台操作另记录可信角色、映射结果、权限版本、会话撤销/生效时间及实际菜单/API 结果，不记录秘密。

一个结算可有多条合法分录。验证是否重复按**业务操作与资金效果**判断，不按“只能有一条数据库记录”判断。

| AC-I18 首登原子性与并发 | 管理员并发回调、重放，绑定/角色写入或会话签发处失败 | 唯一正确绑定和角色，失败不签错误会话；重试不重复用户，不留下需手工修复的普通角色 |

| AC-I20 SSO-only 与最后超管 | Sub2 专用绑定、改登录方式/解绑/移除最后有效超管；另测权威服务失效 | 守卫识别专用绑定且真实登录/API 验证通过后才切换；拒绝主动移除最后有效路径；失效时清晰报警，不删守卫或启用本地后门 |

## 7. 钱包、授权与防重复用例

### 7.1 余额与模型

| 用例 | 输入/动作 | 通过条件 |
|---|---|---|
| AC-B01 钱包展示 | 永久余额、临时余额同时存在 | 单位、精度、可用性和有效期符合 Sub2 权威查询；不把缓存当可花额度 |
| AC-B02 组合扣减 | 仅永久、仅临时、两者都有、都不足 | 完全复用 W02 冻结的 Sub2 规则；Chat 不另算一份扣减顺序 |
| AC-B03 过期边界 | 执行前/期间跨临时额度过期点 | 结果符合 Sub2 时间语义，不能转成永久资金或使用已失效额度 |
| AC-B04 套餐及其他计费因素 | 原 Sub2 配置与新 Chat 策略分别存在 | 普通 Sub2 保持原规则；Chat 用已确认策略一次结算，不叠旧零售倍率；资金/订阅/Key 配额口径正确 |
| AC-B05 同时消费 | Sub2 与 Chat 对同一用户并发合法消费 | 符合 Sub2 已批准并发/余额策略；无 Chat 额外缓存放行或独立扣费 |
| AC-B06 退款归属 | 对已结算操作退款，临时额度可能已过期 | 依权威规则返还和留痕，不任意变成永久余额或重复退款 |
| AC-B07 权威服务故障 | 钱包查询/计费服务暂时失败 | 拒绝需要权威确认的新付费操作，不用本地钱包/公共 Key 兜底 |
| AC-B08 金额完整性 | 修改浏览器金额、价格、倍率、负数/越界参数 | 后端校验，不能改变权威计费或实施未授权调账 |
| AC-P01 用户级归因 | 两个用户使用同一模型 | 每个执行归属正确用户；不能统一记到一个服务账号 |
| AC-P02 模型/组越权 | 前端强行提交未授权模型或组 | Sub2 服务端拒绝；展示可见不等于允许调用 |
| AC-P03 权限即时变化 | 降级用户、移除模型、撤销 Key 后发起/恢复后台执行 | 按契约重新校验，不凭旧缓存或旧任务永久放行 |
| AC-P04 价格变化 | 页面报价后 Chat 价格/玩家优惠或 Sub2 原价变化 | 以已绑定并确认的 Chat 版本结算或按契约重新确认；不静默改价、不继承旧 Sub2 零售倍率、不信客户端价格 |
| AC-P05 Key 泄露防护 | 浏览器网络、日志、错误信息、队列数据检查 | 不含上游或托管 Gateway 密钥，不泄露密码/refresh token |
| AC-P06 模型协议 | 文本、文件、多模态、媒体的每个实际支持协议 | 正确路由与计价；缺少能力明确失败，不偷换到未授权 provider |
| AC-P07 本地组限制 | Chat 限制更严格或尝试扩大 Sub2 范围 | 可收紧，不可扩大；本地管理员配置不能绕过 Sub2 |
| AC-P08 跨底层组统一零售价 | 同模型/协议和相同用量，经两个均已授权但原价不同的 Sub2 组执行 | 同一 Chat 策略/玩家优惠下零售价一致；保留路由与内部成本口径，不扩大准入 |
| AC-P09 玩家优惠隔离 | 用户同时有 Chat 玩家优惠和 Sub2 个人倍率；另测多 Chat 组 | 仅按已发布玩家优惠及其明确取舍规则计算，不额外叠加原 Sub2 零售倍率 |
| AC-P10 策略版本冻结 | 执行中更新价格/玩家组；发布失败、过期或被撤销版本 | 既有执行按绑定版本及约定撤销策略处理；新执行仅用合法已确认版本，无静默回退或临时重算 |
| AC-P11 应用来源隔离 | 同用户分别从 Chat 和普通 Sub2 API 调用，另伪造应用标记 | Chat 用专属策略，普通 API 仍用原规则；未授权请求不能切换应用策略 |
| AC-P12 价格上下文伪造 | 篡改金额、单价、玩家组、用户、模型、版本、摘要或用量 | Sub2 拒绝不可信/不匹配上下文；不能把客户端报价或管理员调余额当消费结算 |
| AC-P13 单策略与结算重放 | 同执行重复提交，另以不同版本/金额重放相同执行 | 只产生应有一次权威资金效果；冲突拒绝，不先扣旧价再补扣/退差价 |
| AC-P14 历史账单与退款 | 结算后价格/玩家组已变化，再查询或退款 | 可追溯原策略/优惠/用量/账务引用；退款沿 Sub2 原资金归属、累计上限及幂等规则处理 |

### 7.2 防双重扣费与故障注入

| 用例 | 注入/动作 | 核心通过条件 |
|---|---|---|
| AC-N01 单次正常执行 | 一次真实模型执行完成 | Sub2 产生应有的一次逻辑结算；Chat 无第二次货币效果，合法拆分分录可解释 |
| AC-N02 重复按钮/并发同操作 | 同一逻辑执行标识并发重放 | 不重复执行受控资金操作；响应可复用或报告已处理中 |
| AC-N03 同键不同参数 | 同幂等键换用户/金额/模型/请求内容 | 拒绝冲突，不能把旧结果授予另一用户或按新参数再扣 |
| AC-N04 提交前故障 | 在确定未派发/未产生权威资金效果时失败 | 无凭空扣费；是否重试按明确状态处理，不凭 HTTP 失败猜测 |
| AC-N05 提交后丢响应 | 权威端已完成，响应在网络丢失 | 查询/核对已有结果，不产生第二次资金效果 |
| AC-N06 进程崩溃恢复 | 派发前后、结算前后分别终止 Chat 或相关服务 | 恢复保留真实状态；UNKNOWN 不被当作未执行重跑 |
| AC-N07 流断线恢复 | 输出中断后恢复既有 run | 重放已有事件，不增加实际 provider 执行和结算 |
| AC-N08 明确重新生成 | 用户发起新的生成 | 新执行可正常收费，与断线恢复区分；不误去重合法新请求 |
| AC-N09 部分输出后取消 | 已有上游执行/用量后取消 | 依 Sub2 实际账务规则结算，不擅自免费、全额退款或再扣一次 |
| AC-N10 未知上游结果 | 网关/provider 超时，不能确定是否执行 | 进入 UNKNOWN，先核对，不盲目重试；无查询能力则不得宣称该门禁已通过 |
| AC-N11 重复支付回调 | 同支付事件重复、乱序通知或补单 | 验签与业务状态正确，入账一次；不同渠道/订单的键作用域不冲突 |
| AC-N12 重复退款/赠送 | 同一退款或赠送业务命令并发重放 | 仅一次权威资金效果，累计退款上限和资金归属符合规则 |
| AC-N13 本地写入旁路 | 旧 API、管理员接口、后台 job、seed、模式回退逐项触发 | 不能恢复 Chat 独立资金写入；不只是 UI 被隐藏 |
| AC-N14 多次合法辅助执行 | 主回答+工具回合+摘要/embedding 等 | 每个真实执行有归因；合法多次结算不被误判，任一执行均无双系统重复收费 |

**取证要点：**同时核对逻辑结算与分录、两类余额和退款/过期事件。不能用“最后余额差不多”或“日志只有一行”证明没有重复扣费。

### 7.3 Sub2 账号池分组与模型选择

以下为 R10 的待执行用例；与 AC-P08/AC-N 系列联合验证价格与防重复，不以组控件可见替代后端约束。

| 用例 | 输入/动作 | 通过条件 |
|---|---|---|
| AC-G01 上游配置与分组身份 | 有权/无权管理员读取保存组列表；同名组、改名组及公有/专属/停用组 | Sub2 账号池类型复用连接；按稳定 ID 保存并校验权限，显示状态/新鲜度；列表可见不等于可授权全部玩家 |

| AC-G03 空选择与新增分组 | 空白名单、配置丢失、Sub2 新增分组、候选池全部不可用 | 不开放全组、不自动加入新组、不借用未选池；明确失败并仍允许有权管理员登录修复 |
| AC-G04 目录同步和上架 | 所选组增加模型、同名不同协议、模型映射变化、尚未配置确认价格 | 自动同步但不自动付费开放；管理员确认上架、规范 ID/协议/来源和价格；执行另做权限检查，展示名单不当作能力/准入证明 |
| AC-G05 组状态与权限变更 | 已选组停用/删除/零可用账号、白名单移除、用户权利撤销；含排队/后台任务 | 新派发及重试重新校验，旧快照不延续撤销权限；按契约处理中途执行；不使用未选池兜底 |
| AC-G06 优先级和跨组回退 | 同模型多个获准组；原 fallback 指向未选组；派发后结果未知 | 只在安全可重试时按优先级切换到交集内目标，最终账号归属可追溯；拒绝越界 fallback，UNKNOWN 先核对不重跑 |
| AC-G07 调度模式及全路径 | Simple/Composite、HTTP/WebSocket、工具循环及辅助/媒体异步任务 | 各路径执行同一最终组约束；不兼容模式失败关闭，不能按平台全池绕过；协议未支持明确失败 |
| AC-G08 配置版本与请求伪造 | 并发更新/旧版本回放、浏览器改 app/UID/group/模型/白名单，普通 Sub2 API 对照 | 服务端确认/拒绝冲突且每次执行有可信版本及最终组/账号审计；新撤销及时生效，无秘密泄露；普通 Sub2 规则不被 Chat 配置改写 |
